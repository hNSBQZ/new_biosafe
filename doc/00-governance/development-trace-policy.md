# 开发留痕、提交与验证规范

## 每阶段必须留下的内容

阶段开始前，在实施计划中把该阶段标记为 `IN_PROGRESS`，并确认设计记录包含：目标、非目标、受影响模块、API/事件、数据结构、风险、回滚方式和验证命令。

阶段结束时，在 `doc/04-progress/YYYY-MM-DD_phase-N_主题.md` 记录：

```markdown
# Phase N - 标题

- 状态：DONE / BLOCKED
- 范围：
- 关键设计：
- 实际变更：
- 数据或接口兼容性：
- 验证命令与真实结果：
- 外部服务验证：
- 提交：<hash> <subject>
- 遗留问题：
- 下一阶段入口：
```

测试报告放在 `doc/05-testing/`，运行日志放在被 Git 忽略的 `logs/`，不要用日志代替结论。

## 提交规则

1. 一次提交只包含一个可解释、可回滚、可验证的功能。
2. 代码与对应测试应在同一功能提交中，阶段总结可以紧随其后单独 `docs:` 提交。
3. 提交前运行 `git diff --check`、相关测试和 `git diff --cached` 安全检查。
4. 不使用 `git add .` 无差别暂存；明确列出文件或受控目录。
5. 不改写已经共享的历史，不执行 destructive reset，不覆盖用户改动。
6. 每阶段提交后保持工作树干净；若保留本地运行产物，应已被 `.gitignore` 排除。

## 远端 RAGFlow 验证规则

- 先用 mock contract test 固定请求和响应模型，再做 live smoke test。
- live smoke test 只能操作本任务创建且名称以 `biosafe-dev-` 开头的资源。
- 创建、上传、解析、检索和删除分别留出超时与失败状态，前端不得伪装同步成功。
- 删除测试资源前记录其 ID；只能删除同一测试流程创建的 ID。
- 任何远端异常都不得泄露请求头或 token。

## 阻塞标准

先自行尝试文档、代码、mock 和只读探测。只有缺少会改变产品行为的决定、连续外部故障或需要破坏性操作时才阻塞；阻塞时记录已尝试内容和恢复入口。
