# Phase 6 - 异步答案修正设计

## 目标与边界

在成功的 direct/RAG 问答完成并写入 `chat_history` 后，将原始问题和系统答案快照放入进程内有界异步队列，由独立配置的强模型重新回答。模型建议只供管理端展示、审计和人工采纳，不覆盖 `corrected_answer`，不写入 RAGFlow，也不参与后续在线回答。

非目标包括历史答案短路、自动发布审核问答、查询改写、本地检索，以及对 FuncCall、失败或取消记录自动生成答案。

## 受影响模块

- `biosafe/config.py`：增加独立修正模型配置；队列容量、worker 数和关闭超时使用代码默认值，环境变量只保留当前 `.env` 的修正模型字段。
- `biosafe/integrations/correction/`：封装 OpenAI Responses API 与 web search，解析结构化修正答案和公开来源。
- `biosafe/storage/`：迁移 `answer_correction` 简单任务表；保存问题/原答案快照、状态、模型答案、引用、时间和脱敏错误。
- `biosafe/application/`：有界 `asyncio.Queue` dispatcher；QueryService 仅在 direct/RAG 成功落库后非阻塞提交。
- `services/api/`：lifespan 启停 worker；历史详情附带模型修正；提供失败或旧记录的显式重新入队接口。
- `web/`：历史详情展示任务状态、模型建议和来源；“采用建议”只填充人工编辑框，仍需点击保存。

## 接口与状态

`HistoryItem` 新增可空 `auto_correction`：

```text
id, history_id, status, model, can_answer, answer,
cannot_answer_reason, citations, error,
enqueued_at, started_at, finished_at
```

`POST /api/history/{history_id}/auto-correction` 对成功的 direct/RAG 历史发起或重试任务；不存在返回 404，不可修正记录返回 409，dispatcher 未配置返回 503。重复提交 pending/running 任务保持幂等。

任务状态：`pending -> running -> success | parse_error | request_error`；队列满为 `dropped`。应用重启时将未完成任务重新入队，超过队列容量的任务标记为 `dropped`。

## 数据与安全

`answer_correction` 位于同一个 SQLite 数据库，不建立外键，`history_id` 唯一并作逻辑关联。保存修正模型答案、公开来源 JSON 和有限长度错误；不保存授权头、API key 或完整模型响应。配置仅从环境变量读取，repr 隐藏密钥。

## 风险与回滚

- 进程内队列不支持多实例全局调度；单实例当前部署可用，重启恢复未完成任务。未来多实例应换持久化队列。
- Responses API 或 web search 不兼容时任务进入稳定失败状态，不影响问答响应。
- 回滚可关闭 `CORRECTION_ENABLED`；新增表和响应可空字段可保留，不影响旧数据和现有客户端。
